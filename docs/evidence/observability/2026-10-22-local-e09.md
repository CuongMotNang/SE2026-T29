## Fault request

The backend was recreated with a bounded error fault:

```text
BOOKING_FAULT_MODE=error
BOOKING_FAULT_RATE=1.0
BOOKING_FAULT_UNTIL=2026-10-22T15:57:00.6634874Z
```

At `2026-10-22T15:52:07.0151436Z`, `POST /api/appointments` returned HTTP `500` with
`Injected booking failure`. The request log contained:

| Field | Observed value |
| --- | --- |
| Trace ID | `15ad9df4686f7df9c7d5a2c47fb38e15` |
| Route template | `/api/appointments` |
| Status | `500` |
| Release / commit | `dev` / `local` |
| Duration | `14.692 ms` |

Additional bounded requests were used to verify the rate expressions. Fault injection was then
disabled and the backend container was recreated with `BOOKING_FAULT_MODE=off`.

## Metrics

The first live query exposed a mismatch between the PromQL and the names exported by the current
OpenTelemetry stack. After correcting the rules and dashboard, Prometheus returned:

| Query | Observed value |
| --- | --- |
| `sum(rate(http_server_duration_milliseconds_count{service_name="booking-api"}[1m]))` | `0.1111160496` requests/s |
| `booking:http_requests:rate1m{http_target="/api/appointments"}` | `0.1313444444` requests/s |
| `booking:http_5xx_ratio:rate1m` | `0.3846153846` |
| `booking:http_request_duration_seconds:p95_5m` | approximately `0.0049 s` |

`promtool check rules` passed all six rules, the Prometheus reload endpoint returned HTTP `200`,
and the recording rules produced non-empty results from live telemetry.

## Trace and log correlation

For one of the bounded error requests, Loki returned an `http_request` log stream with:

| Field | Observed value |
| --- | --- |
| Trace ID | `3354dc92149c0180abefaffdda8020e8` |
| Route | `/api/appointments` |
| Status | `500` |
| Release | `dev` |

Querying Tempo by that exact trace ID returned five spans. The server span and
`booking.create` span had `STATUS_CODE_ERROR`. This confirms that the log and error trace can be
joined by trace ID and agree on route, status and release.

## Database spans

The local run also detected that SQLAlchemy 2.1 was outside the supported range of the installed
OpenTelemetry SQLAlchemy instrumentation. After constraining SQLAlchemy to 2.0.x and rebuilding,
the backend ran with SQLAlchemy `2.0.55` without the instrumentation warning.

A successful create-booking request with trace ID `ebd427faa7eab38bc976fadd7585968e`
produced nine spans, including `booking.create`, `connect`, `SELECT` and `INSERT`. The complete
business smoke test then passed readiness, version, create and cancel checks.
